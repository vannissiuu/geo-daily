2) **推算漏跑日期**：本任务固定为每个工作日（周一至周五）10:00 执行一次，周六、周日为计划内不执行日，不计入漏跑。以「今天 10:00 触发」为基准，向前推算：从 `last_run_at` 所在日期的次日 10:00 起，到【昨天 10:00】止，仅把落在【工作日（周一至周五）】内的、应触发但未触发的「日期」计入漏跑日期（自动跳过周六、周日）。（例：`last_run_at`=某周五、今天周一触发 → 中间周六周日为计划跳过、不补；`last_run_at`=周三、今天周五 → 漏跑周四一天。）
3) **补跑上限**：最多补 **3 天**（按时间倒序，先补最近的漏跑日）。若漏跑 >3 天，只补最近 3 天，更早的日期不补、也不在文档/回复里额外提示。
4) **逐一补跑**：对每一个漏跑日期，以【该漏跑日期】作为「当日」走完整流程——即：以该日期为采集视角（检索该日期附近的近 5 天动态、但写入时归到该日期块）、执行【零、去重前置】（与该日期及更早数据去重，避免和正常日报重叠）、生成该日期的 HTML 报告、推送飞书私聊（BOT 身份，与正常日报一致）、并写入 `GEO每日动态_数据.md` 对应日期块、汇总进飞书回溯文档。补跑日报**正常推送，无需在报告/文档里特别标注「补跑」字样**（静默补）。
5) **防重跑锁**：补跑依据 `last_run_at` 推算，已补的日期不会重复补；所有补跑完成后，`last_run_at` 会随本次成功运行自然更新，下次触发以此为准。
6) **与周结的关系**：若某周一因设备离线漏跑，导致该周一本应生成的「上周」周结缺失，则按下方【周结自愈 · 方案 B】在下个周一补齐，保证周结不缺口（详见周结子流程第 0 步）。
7) **补跑同样遵守全部既有规则**：链接真实性铁律、分类解析自检、飞书 h3 防吞、命名规范（Part1/Part2/Part3）、用户手动 callout 原样保留等，与正常日报完全一致，不得降级。
8) **执行顺序**：先完成上述全部漏跑补跑，再执行今天的正常日报流程（【零、去重前置】起）。

【零、去重前置（必须最先执行，否则不得生成）】
1. 在当前工作目录下读取文件 `GEO每日动态_数据.md`（若不存在则新建空文件，含文件头注释即可）。该文件是全部历史动态的【单一数据源】，格式见【四-B】。
2. 本次搜集到的候选条目，凡是出现以下任一情况，一律【剔除、不得再次推送】：
   a. 标题或链接命中数据源中已有条目（同一篇文章/同一报道源）；
   b. 属于数据源已报道过的【同一具体事件/同一发布动作】且无重大新进展；
   c. 标题/核心内容高度雷同于数据源已有条目。
3. 只有当候选中存在【未在数据源中、且确为近 5 天新动态】的条目时，才进入后续生成流程；若全部候选都在数据源中，应扩大检索、寻找真正的新内容，实在没有新内容则当日少发并注明"今日无新增时效性动态"。

【一、信息搜集 —— 时间范围是硬性要求，必须严格执行】
关注 AI GEO 领域的最新动态，侧重 GEO 新技术、GEO 相关舆论观点方向。
时效纪律（务必遵守）：

5. 数量规则：筛选 3-5 条。若最近 5 天内确实凑不满 3 条真正有时效性的信息，宁可少发（如 2 条），并在报告顶部注明"今日 GEO 时效性动态较少"，绝不允许用旧文章凑数。

【一-B、今日精华提炼（运行时 AI 综合归纳 · 必须执行）】
在按【一】完成采集、分类、链接核验后，必须对【当日】全部条目做「趋势级」提炼，生成「今日精华」并写入数据源（供飞书 Part1 与 HTML 共用，保证两处一致）。提炼规则：
- **收敛归纳优先**：若当日多条条目指向同一趋势 / 同一主题，合成 1–3 条【趋势级】要点（概括性、带判断、面向方案商视角），【不要】逐条复述每条消息的标题。这是「今日精华」的设计原意——把分散消息归纳成可一眼抓住的当日主线。
- **独立则逐条**：若当日条目 ≤3 条且彼此主题不同，则每条一个分点（对应消息），这没问题。
- **纯文本、不带分类标签**：每条精华分点只写要点文字，【严禁】加 `[分类]` / `【平台动态-…】` 这类标签（分类标签只属于下方带序号的逐条详情标题，今日精华永不带标签）。**同样严禁加 ①②③ / 1)2)3) / （一）（二）等任何编号前缀**——精华分点保持纯 `- ` bullet 即可；没有约定过的输出格式不要擅自添加，格式不统一会严重伤害报告专业性（2026-08-11 教训：曾误加 ①②③ 被用户批评）。脚本层 strip_hl_tag 会防御性剥离，但运行时 AI 写数据源时就不该加。
- 写入数据源格式见【四-B 数据文件格式】的「每日精华块」。

【三、生成 HTML 报告】

  4. **【信源优先级】** 优先采用权威/中立媒体（完整白名单见顶部【2026-09-23 方案 C】第 3 条，名单外不得作为删除理由）；**软文不得"见即删"**——须按顶部第 1 条 A/B/C 三级分类处置并履行第 2 条换源义务：仅 A 类（纯自夸无信息量）可整条删除；B 类须剥离事实内核换独立源后入报；C 类（含可复核数据的一手实测/研究）直接收录，不得因发布主体是服务商或技术社区而剔除。

## 一、第 6 类「平台动态」定义与边界
- **平台动态**：被优化对象（豆包 / DeepSeek / Kimi / 千问 / 文心 / 元宝 / Google（AI Mode·AI Overviews）/ ChatGPT（OpenAI）/ Perplexity / Claude 等大模型平台）**自身**的算法、信源、引用、收录、爬虫、商业化策略变更。
- **边界（避免与「新技术」重叠）**：主语是「做 GEO 的工具 / 服务商」（如 Pepper、Cloudflare 的 AEO 看板、GMO Local GEO Dash!、Adobe LLM Optimizer）归「新技术」；融资 / 合作 / 渠道类归「市场动态」。
- **判定口诀**：主语是被优化平台 → 平台动态；主语是做 GEO 的工具 → 新技术 / 市场动态。
- **【排除 · 检索阶段即过滤】被优化平台的「通用履约 / 交易 / 生态能力」发布（如开放 Agent 接入、自带支付与订单基建、寄快递 / 租房租车等履约能力、C 端会员收费）属通用 AI 助手生态动作，不改变其如何引用 / 推荐第三方 GEO 内容，不纳入 GEO 动态跟踪**。（2026-08-11 教训：曾误纳「千问开放平台上线」为平台动态，实则与 GEO 可见度机制无关，已剔除。）
- **【明确纳入 · 2026-09-23 边界修正，优先级高于上一条排除项】** 凡改变"平台如何找到、选择、引用、呈现第三方内容"的变更，**一律属平台动态，不得以"模型更新 / 产品发布"为由排除**，包括：① 对第三方内容的检索机制升级（联网检索深度、可调度子 Agent 数、可交叉核验网页数、检索并发策略）；② 证据溯源 / 引用标注 / 权威信源优选机制的引入或调整（如"证据溯源""权威信源检索""时效判断""数据核验"）；③ 引用 / 收录 / 排序 / 推荐位的规则与权重变更；④ 爬虫协议、robots、收录周期变更。（2026-09-23 教训：豆包 2.1 Pro 0915 强化证据溯源与权威信源检索，曾被误当模型更新排除，实为教科书级平台动态，已按发布日 9/16 补录。）
- **判定口诀（升级版）**：主语是被优化平台 **且** 变更改变"第三方内容如何被找到 / 选中 / 引用 / 呈现" → 平台动态；主语是被优化平台但只是"自己多了什么功能 / 能卖什么" → 不纳入；主语是做 GEO 的工具 → 新技术 / 市场动态。
- 写入数据源时，平台动态条目标题应含平台名（如「豆包」「Google」），渲染脚本会自动在 Part1 加【平台动态-<平台>】标签（如【平台动态-豆包】），无需手工加标签。
