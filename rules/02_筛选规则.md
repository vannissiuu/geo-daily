# 02 筛选规则

> 本文件管：每天从候选里"收哪条、不收哪条"——时效窗口、去重、链接核验、软文分级处置、国内占比告警、条数、缺口自适应窗口。
> 去哪里找、白名单 / 禁采 / 聚合页清单见 `01_信源与巡检.md`；归哪类见 `03`；怎么写、JSON 格式、机检见 `04`。
> **优先级**：第 5 节软文分级（方案 C，冻结）> 第 1–3 节时效 / 链接铁律 > 其他。冲突按此顺序取舍，不自行折中。

## 0 运行与定位

0.1 **仅周一至周五运行**（法定节假日照常运行）。周六日不运行、不生成日报，不算漏跑。
0.2 **D** = 运行当天。
0.3 判的是"**这条信息是不是真的**"，不是"这篇稿子是不是软文"（详见第 5 节）。
0.4 读者定位：GEO 解决方案提供商，用日报把握行业最新最快最有影响力的 GEO 信息，调整产品方向、优化向客户卖进的策略。侧重 **GEO 新技术、GEO 相关舆论观点方向**；与此无关的不收。

## 1 时效窗口（硬性）

1.1 **窗口 [S, D]，含两端点**。S 默认 = D−5（例：D = 2026-10-12，窗口 10-07 至 10-12）；漏跑后的 S 见第 7 节。
1.2 **48 小时优先**：窗口内优先选最近 48 小时的新闻 / 观点。
1.3 **日期双检（写入前对每条必做）**：① 事件 / 发布动作本身的日期 ∈ 窗口；② **主链接（`links[0]`）页面自身标注的发布日期** ∈ 窗口且 ≤ D，`published` 取它。辅助链接只需与事件直接对应（可为无日期的官方文档）。主链接页面日期超窗不得入报（教训：一手数据页标注 08-06 被用户指出）。
1.4 **旧事件被近期重新报道不收**，除非有实质新进展（以新进展的日期为事件日期）。
1.5 **无法确认发布日期的一律不收**；列表页相对时间（"3 小时前"）须换算成具体日期。
1.6 剔除"GEO 全解析 / 终极指南 / 趋势预测"类长青科普长文和无日期的服务商榜单；不得用旧文章凑数。

## 2 去重

2.1 **去重前置**（最先执行）：先读仓库全部历史 `data/daily/*.json`。候选命中任一情况即剔除：a. 标题或链接与历史条目相同（同一篇文章 / 同一报道源）；b. 同一具体事件 / 同一发布动作且无重大新进展；c. 标题 / 核心内容与历史条目高度雷同。
2.2 去重判据**仅限"同一事件"**：不得因"同一发布主体 / 同一服务商系列稿"整类去重——同主体的不同事实（两次不同实测、两个不同标准、两个平台的机制变更）应分别收录。
2.3 **同源多投算 1 条**：多标题、多站点但同一套话术、同一结论的稿件视为同一事件，最多收 1 条（见 5.5）。
2.4 同一天内不得出现 (date, title) 完全相同的两条。
2.5 候选全在历史中时应扩大检索找真正的新内容；实在没有则少发或记无动态。**去重优先于凑数。**

## 3 链接真实性与核验铁律

3.1 **只用工具实际返回的 URL**：必须来自 WebSearch / WebFetch 实际返回，原样复制，严禁编造、猜测、改写、拼接。
3.2 **每条链接写入前必须 WebFetch 打开核验**：(a) 不是 404 / 页面不存在；(b) 内容与本条主题对应，非文不对题；(c) 页面标注的标题 / 日期与所记一致。不满足则剔除该链接；整条无其他可靠源则整条不入报。假链接、失效链接比无链接危害更大。
3.3 **一条消息 = 至少一个独立、直接对应的信源链接**：点开后页面主体必须就是该条事件本身；聚合导航页 / 多条目列表页不合格，须换独立报道。
3.4 **禁止多条消息共用同一链接**（忽略查询参数），含当日内和与历史条目共用（机检项，见 `04`）。教训：三条消息共用一个追踪站被用户质疑。
3.5 **聚合页 / 追踪站只用于发现线索**，不得作信源链接。**禁采名单**（`01` 第 7 节）一律不得作最终链接，只可顺藤摸瓜。理由：WebFetch 走代理能取到内容 ≠ 用户浏览器可打开，且历史上频繁 404 / 文不对题。
3.6 **同顺号**（`t.10jqka.com.cn`）可用，但须逐条 WebFetch 核验有效且内容对应；不设次日复验。
3.7 **用户实际可访问**（用户实测为准）：
  - 凡疑似有地域限制 / 反爬 / Cloudflare 或人机验证页 / 登录墙的站点一律不用（教训：searchengineland.com 等防护站 WebFetch 可读但用户打不开）。
  - Claude 无法从中国大陆实测，故只能看：WebFetch 返回的是否正文（而非验证页 / 空壳 / 跳转页）、是否已知强防护站、历史上有无用户反馈不可访问。**拿不准偏保守，换同一事件的其他独立源**；换不到就删条。
  - 优先用实测可访问的独立中立源（历史示例：blog.google、dev.to、worldprogramming.org、victorinollc.com）。
  - 用户反馈某域名打不开 → 追加进 `01` 禁采名单并同步 `config/sources.json`，之后一律不用。
3.8 **无链接 / 无可访问链接的条目一律不入报**，宁可删条；不再允许"暂无可用公开链接"。
3.9 **信源优先级**：权威 / 中立媒体 > 官方发布（官方博客 / 更新日志 / 开发者文档 / 标准发布方）> 一手研究 > 企业发布稿（按第 5 节分级处置）。

## 4 国内信源白名单的用法与占比告警

4.1 白名单（`01` 第 7 节）只是**"优先采信"清单，不是准入清单**；名单外不得作为删除理由，按三项判定，通过即可采用：① **可溯源**（明确发布主体与日期）；② **有可核验信息量**（具体数字 / 机制 / 时间）；③ **用户可访问**（3.7）。
4.2 **反软文判据看"内容特征"而非"主体身份"**：只因发布主体是 GEO 服务商 / 云厂商社区 / 企业公众号就剔除属**违规剔除**；真正的删除判据是"无第三方可核事实 + 通篇推销（留资表单 / 咨询电话 / 课程售卖）"。
4.3 **白名单内 ≠ 直接采信**：同一服务商同一套话术投放多家白名单媒体，按 5.5 处理。
4.4 **国内条目占比告警**：`domestic_ratio` = `region` 为国内的条目占比（当日值与近 30 日滚动值均记录，口径见 `04` 5.2）。**任一 < 40% 只告警不拦截**，提示中文检索池疑似被过度淘汰；运行者须复核：软文是否已按 A / B / C 分级？B 类是否执行了换源义务？（教训：旧规则下含国内信源条目占比 7 月 72.5% → 9 月 29.0%，日均条数 3.33 → 1.82。）

## 5 软文三级分类处置（方案 C · 冻结语义）

覆盖此前所有"遇软文即删 / 白名单外即删"的旧表述。

### 5.1 总原则
**判的是"这条信息是不是真的"，不是"这篇稿子是不是软文"。** 命中软文 ≠ 信息作废；旧规则把"稿件属性"误当"信息属性"，使软文密度天然高的中文检索池被系统性过度淘汰。

### 5.2 三级分类（强制：先分类再处置，禁止跳过分类直接删）
| 类 | 特征 | 处置 |
|---|---|---|
| **A 类 · 纯自夸无信息量** | 通篇自吹，无具体事实 / 数据 / 时间 / 事件（如"XX 成为 GEO 标杆""GEO 服务商 TOP10 榜单"且无第三方数据支撑） | **整条删除** |
| **B 类 · 软文外壳 + 真实事实内核** | 服务商 / 企业口吻，但内含可溯源的具体事实（某平台某日上线某机制、某项实测的具体数字、某标准的具体编号与发布方） | **禁止整条删除**。剥离事实内核 → 用该事实关键词重新检索独立中立报道 → **换源后正常入报**；确无独立源时允许保留该软文源链接，但须在标题或摘要中标注「（信源为企业发布稿）」 |
| **C 类 · 一手实测 / 研究** | 服务商或技术社区发布，含具体方法论与可复核数据（如"65 题 × 5 模型 × 联网的 650 次 AI 回答引用信源结构实测"） | **直接收录**，不得因"发布主体是服务商 / 云厂商社区"而剔除 |

**C 类说明**：一手引用数据只有具备批量调用条件的服务商 / 技术社区能产出，是方案商价值最高的「行业方法论」素材。判据看【是否有可复核的数字与方法】，不看【谁发的】。

### 5.3 换源义务（B 类强制动作，不可省略）
任何因"疑似软文"准备剔除的候选，必须先做**至少 1 次换源检索**（用事实内核关键词：标准编号、平台机制名、实测结论短语），换到独立中立源则入报。**只有"换源失败 且 属 A 类"才允许删除**（矩阵软文例外，见 5.5）。禁止"看到服务商域名就删"的懒剔除。换源检索须在采集日志 `source_swaps` 留痕。

### 5.4 与 JSON 字段的对应、判定流程
- `soft_class` 取 `无 | B | C`；A 类整条删除，不进 `entries`，只记入 `data/runs/` 落选记录。
- B 类**换源成功**：`soft_class` 记 `B`，`source_type` 记换到的源类型。
- B 类**确无独立源**保留企业发布稿：`source_type` = `企业发布稿`，标题或摘要必须含「（信源为企业发布稿）」（机检项）。
- C 类：`soft_class` = `C`，`source_type` 通常为 `一手研究`。
- 流程：非软文口吻 → `无`，常规核验；软文口吻 → 先分 A / B / C：A 换源一次，失败则删；B 剥离事实内核后换源，失败则保留企业发布稿并标注（矩阵软文除外）；C 直接收录。

### 5.5 反「软文矩阵 / 同源多投」条款（特别规定，优先于 B 类通则）
同一服务商把**同一套话术**（同一份"六维框架 / TOP 榜 / 全景测评"，结论内定指向自己）以不同标题同步投放到多家白名单媒体（如 IT之家、凤凰网科技、今日头条、搜狐号）时：
- **不得因"发布主体在白名单内"直接采信**。通篇结论指向同一服务商、无第三方可复核数据、或虽引用第三方数据（标准编号 / 行业报告数字）但仅作背书不作论证的，判为**矩阵软文（B 类子类）**。
- **处置**：只保留**事实内核**（如标准编号 AIIA/T 0277-2026、易观 / 艾瑞 / CNNIC 的市场规模与占比口径），**换源到一手出处**（信通院官网 / 报告原文 / 标准原文）后方可入报；**换不到一手源则整条删除，且不得保留软文源链接、不适用 B 类"保留企业发布稿"**（矩阵稿"事实"多为转述，可核性差）。
- **同源多投去重**：同一套话术与结论的多篇稿件视为同一事件，最多收 1 条。
- **对照**：真正的一手实测（方法可复现：问题集 / 模型清单 / 样本量 / 统计口径 / 局限说明，结论不含自我推销）按 C 类**直接收录**，不得因发布在云厂商社区 / 技术社区 / 个人博客而剔除（实例：腾讯云开发者社区"650 次 AI 回答引用信源结构实测"）。

## 6 数量规则

6.1 每日 **3–6 条**，同一天内按**重要性**排序（对方案商的影响力优先，同等则近 48 小时优先），`id` 顺序即排序。
6.2 **宁缺毋滥**：凑不满 3 条真正有时效性的信息就少发，绝不用旧文章凑数。
6.3 不足 3 条（1–2 条）：`status = few`，网站提示"今日 GEO 时效性动态较少"。
6.4 **0 条**：`status = none`，`entries` 与 `highlights` 为空数组；采集日志 `notes` 记"已执行全量检索，窗口内无符合铁律（真实可溯可访问 + 窗口内 + 独立信源 + 非软文）的净新条目"。**工作日不得不写文件**——无动态哨兵用于区分"已执行但无动态"与"漏跑"。
6.5 超过 6 条程序只告警、不拦截。

## 7 缺口自适应窗口（取代逐日补跑）

7.1 每次运行**最先**读仓库中最近一个 `data/daily/*.json` 的日期 L。
7.2 若 L 是上一个工作日或今天，窗口照常 [D−5, D]；若中间漏了工作日，起点 **S = min(D−5, L+1)**，但**不早于 D−7**。
7.3 漏跑期间的消息记在当天 D 的文件里，**不为漏跑日单独建文件**；第 1 节全部时效规则照用（以 S 为窗口下界）。已存在 `data/daily/{D}.json` 时不重复生成（重跑须显式确认）。
7.4 周度总结的自愈补跑（最多 1 份）见 `05`。
